# 代码审查

对指定文件或 PR 进行全面的代码审查。

## 审查范围

目标: `$ARGUMENTS`

- 如果是文件路径 → 审查该文件
- 如果是 PR 号 → 审查 PR 变更
- 如果为空 → 审查 `git diff main` 的变更

## 执行步骤

### 1. 获取变更内容

```bash
# 如果未指定参数，审查相对 main 的变更
git diff main...HEAD --stat
git diff main...HEAD

# 如果指定了文件
git diff main...HEAD -- <file>

# 如果是 PR 号
gh pr diff <PR号>
```

### 2. 质量检查

审查维度：

```markdown
### 代码质量
- [ ] 命名清晰准确（函数动词开头、类名词）
- [ ] 函数长度不超过 40 行
- [ ] 嵌套层级不超过 3 层
- [ ] 无重复代码（DRY）
- [ ] 注释解释"为什么"而非"做什么"
- [ ] 错误处理完整（不吞异常）
- [ ] 无调试代码残留（console.log、print、TODO）
```

### 3. 安全审查

```markdown
### 安全检查
- [ ] 无硬编码密钥/密码/Token
- [ ] 用户输入已验证和清理
- [ ] SQL 查询使用参数化
- [ ] 无 eval/exec/动态代码执行
- [ ] 文件操作路径安全（无穿越风险）
- [ ] 敏感数据使用安全存储（Keychain/环境变量）
- [ ] HTTP 请求使用 HTTPS
```

### 4. 性能分析

```markdown
### 性能检查
- [ ] 无 N+1 查询问题
- [ ] 无不必要的全量数据加载
- [ ] 大列表使用虚拟滚动或分页
- [ ] 无内存泄漏风险（事件监听器清理）
- [ ] 异步操作不阻塞主线程
- [ ] 缓存策略合理
```

### 5. 测试检查

```markdown
### 测试覆盖
- [ ] 新功能有对应测试
- [ ] 边界情况已覆盖
- [ ] 错误路径已测试
- [ ] 测试描述清晰
- [ ] 无测试中的硬编码等待（sleep）
```

### 6. 最佳实践

```markdown
### 最佳实践
- [ ] 符合项目编码规范
- [ ] 正确使用框架特性（React hooks、SwiftUI 等）
- [ ] 依赖注入而非硬依赖
- [ ] 接口设计遵循最小知识原则
- [ ] 类型安全（无 any、无强制解包）
```

## 报告格式

```markdown
## 代码审查报告

### 概览
- 审查范围: [文件/PR]
- 变更文件数: X
- 新增行数: +X / 删除行数: -Y

### 严重程度统计
| 级别 | 数量 | 说明 |
|------|------|------|
| CRITICAL | X | 必须修复，阻塞合并 |
| WARNING | X | 建议修复 |
| INFO | X | 改进建议 |

### 问题列表

#### CRITICAL
1. `[文件:行号]` — [问题描述]
   - 原因: [为什么是问题]
   - 建议: ```[修复代码片段]```

#### WARNING
1. `[文件:行号]` — [问题描述]

#### INFO
1. `[文件:行号]` — [改进建议]

### 总体评价
- 代码质量: [优秀/良好/需改进]
- 安全性: [通过/有风险]
- 可维护性: [高/中/低]
- 建议: [合并/修改后合并/需要重做]
```

## 重要原则

- 审查意见必须具体，附代码位置和修复建议
- 区分"必须修复"和"建议改进"
- 认可写得好的代码，不只指出问题
- 不做风格偏好层面的主观批评
- 不要求重构无关代码
