# 功能实现计划

根据用户需求 `$ARGUMENTS`，创建结构化的实现计划。

## 执行步骤

### 1. 需求分析

- 提取 `$ARGUMENTS` 中的核心需求
- 识别功能边界：包含什么、不包含什么
- 列出隐含需求（错误处理、边界情况、性能要求）
- 确认技术约束（语言、框架、现有依赖）

输出格式：

```markdown
## 需求摘要
- 核心功能: [一句话描述]
- 用户故事: 作为 [角色]，我希望 [功能]，以便 [价值]
- 边界: 包含 [...] / 不包含 [...]
```

### 2. 代码库探索

- 搜索相关文件和模块：`Glob` + `Grep`
- 理解现有架构和目录结构
- 识别可复用的组件和模式
- 确认需要修改的文件列表

输出格式：

```markdown
## 受影响文件
- `path/to/file.ts` — [修改原因]
- `path/to/new-file.ts` — [新建原因]
```

### 3. 架构设计

- 选择设计方案，说明 trade-offs
- 定义接口/数据结构
- 绘制模块依赖关系
- 确认与现有代码的集成方式

输出格式：

```markdown
## 设计抉择

| 方案 | 优点 | 缺点 | 选择 |
|------|------|------|------|
| 方案 A | ... | ... | ✅ |
| 方案 B | ... | ... | |

## 数据流
[输入] → [处理] → [输出]
```

### 4. 任务拆分

将实现拆分为可独立执行的子任务：

```markdown
## 任务列表

### T1: [任务名称]
- 描述: [具体做什么]
- 文件: [涉及文件]
- 预计复杂度: 低/中/高
- 依赖: 无 / 依赖 T{n}

### T2: [任务名称]
...
```

拆分原则：
- 每个任务可独立测试验证
- 单个任务改动不超过 3 个文件
- 优先完成核心路径，再处理边界情况

### 5. 风险评估

```markdown
## 风险清单

| 风险 | 可能性 | 影响 | 缓解措施 |
|------|--------|------|----------|
| ...  | 高/中/低 | 高/中/低 | ... |
```

### 6. 输出计划

将完整计划写入 `plan.md`，结构如下：

```markdown
# 实现计划: [功能名称]

## 需求摘要
[步骤 1 输出]

## 受影响文件
[步骤 2 输出]

## 设计抉择
[步骤 3 输出]

## 任务列表
[步骤 4 输出]

## 风险评估
[步骤 5 输出]

## 验收标准
- [ ] [标准 1]
- [ ] [标准 2]
```

## 重要原则

- 不写代码，只做规划
- 每个设计抉择必须说明为什么
- 风险评估必须诚实，不回避问题
- 任务拆分粒度适中，不要过细也不要过粗
- 如需求不明确，主动提问而非假设
