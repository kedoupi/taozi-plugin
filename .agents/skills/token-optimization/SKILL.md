# Token 优化指导

控制 Token 消耗，在质量和成本之间取得平衡。

## 模型选择策略

| 模型 | 适用场景 | 占比建议 |
|------|----------|----------|
| Sonnet | 日常开发、代码生成、调试、重构 | 80%+ |
| Opus | 复杂架构设计、跨系统 debug、核心算法 | 10% |
| Haiku | Subagent 任务、简单查询、格式转换 | 10% |

### 何时用 Opus

- 多模块架构决策
- 跨 3 个以上系统的 bug 定位
- 安全敏感逻辑（认证、支付）
- 性能瓶颈根因分析

### 何时用 Haiku (subagent)

- 文件搜索和分类
- 格式转换（JSON/YAML/CSV）
- 简单文本替换
- 生成模板代码

## 推荐环境变量

```bash
# 限制思考 token 数量，防止过度推理
export MAX_THINKING_TOKENS=10000

# 自动压缩阈值（剩余 50% 上下文时触发）
export CLAUDE_AUTOCOMPACT_PCT_OVERRIDE=50
```

## 压缩时机

### 应该压缩的时机

```
研究完成 → 实现前        # 研究阶段的信息可以精炼
里程碑完成 → 下一个前    # 阶段切换是天然断点
Bug 定位完 → 修复前      # 调试日志不需要保留
长对话 > 30 轮          # 早期对话已经内化到代码中
```

### 不该压缩的时机

```
实现中途（改到一半）     # 正在使用的上下文会丢失
Debug 中间（还没定位到） # 关键线索可能被丢弃
多文件协调编辑时         # 文件间依赖关系需要完整保留
```

## 上下文压缩策略

压缩时应保留的关键信息：

1. **当前任务** — 正在做什么、目标是什么
2. **关键决策** — 已做出的架构/设计选择
3. **活跃文件** — 正在编辑的文件路径和当前状态
4. **未解决问题** — 待处理的 bug 或待办项
5. **分支信息** — Git 分支名和提交状态

可以丢弃的信息：

1. 早期探索中被否决的方案
2. 已解决的中间问题
3. 工具调用的完整输出（保留结论即可）
4. 重复的确认信息

## MCP 管理

```
推荐上限:
- MCP Server 数量 < 10
- 总 Tools 数量 < 80
```

过多的 MCP 会：
- 占用系统提示空间（每个 tool 约 200-500 tokens）
- 增加 tool 选择的不确定性
- 降低响应速度

**建议**: 只启用当前项目需要的 MCP，定期审查。

## 中文 Token 效率

| 内容类型 | Token 效率 |
|----------|-----------|
| 英文代码 | 1 字符 ≈ 0.3 token |
| 英文文本 | 1 单词 ≈ 1.3 token |
| 中文文本 | 1 字符 ≈ 2-3 token |

### 优化技巧

- 代码注释用英文可节省 50%+ tokens
- 文档和说明用中文（可读性优先）
- 避免大段中文放在系统提示中，用简短关键词代替
- 长文档放文件中，提示中只引用路径

## 常见浪费模式

| 浪费模式 | 节省方法 |
|----------|----------|
| 重复读取同一文件 | 读一次，记住关键信息 |
| 大文件全文读取 | 先看目录结构，按需读取 |
| 不必要的工具调用 | 先推理是否真的需要 |
| 过长的问题描述 | 精简到核心需求 |
| 多次格式转换 | 一次到位 |
