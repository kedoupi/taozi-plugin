# TDD

对 `$ARGUMENTS` 严格执行 RED → GREEN → REFACTOR 循环。

## 何时使用

- 实现新功能、修复 bug 且适合测试先行
- 需求清晰、行为可验证
- 希望用测试约束设计，避免过度实现

## 核心原则

- **测试先行**：必须先写失败的测试，再写实现
- **最小实现**：只写刚好让测试通过的代码
- **小步迭代**：每次只加一个测试用例
- **重构安全**：所有测试通过后才重构，重构后立即验证
- **永远不要**在 RED 阶段写实现；在 GREEN 阶段过度设计；在 REFACTOR 阶段改变行为
- 每个循环不超过 5 分钟（超过说明功能点太大）

## 执行流程

### 阶段 1: RED（写失败测试）

1. 理解需求，拆分为小功能点
2. 选择当前最小的可测试功能点
3. 编写测试文件，描述期望行为

**检查清单**：

- [ ] 测试文件已创建
- [ ] 测试描述了期望的输入/输出行为
- [ ] 运行测试 → 确认失败（退出码非零）
- [ ] 失败原因正确（断言失败而非编译错误）

```bash
# TypeScript: npx vitest run --reporter=verbose
# Python:     pytest -xvs
# Go:         go test -v -run TestXxx
# Swift:      xcodebuild test -scheme ...
```

### 阶段 2: GREEN（最小实现）

1. 编写最少代码使测试通过
2. 不考虑优雅、性能、扩展性
3. 可以硬编码返回值（如果这是最简单的做法）

**检查清单**：

- [ ] 实现代码已编写
- [ ] 运行测试 → 全部通过
- [ ] 没有添加多余的代码
- [ ] 没有提前优化

### 阶段 3: REFACTOR（重构）

1. 在测试全部通过前提下重构
2. 消除重复、改善命名、优化结构
3. 每次重构后立即运行测试

**检查清单**：

- [ ] 重复代码已消除
- [ ] 命名清晰准确
- [ ] 函数职责单一
- [ ] 运行测试 → 仍然全部通过
- [ ] 没有改变外部行为

### 循环

重复 RED → GREEN → REFACTOR，直到功能完成。

## 示例 TDD 会话

```
循环 1: 基本功能
  RED:      测试 "空列表返回空结果"
  GREEN:    return []
  REFACTOR: 无需重构

循环 2: 正常路径
  RED:      测试 "有效输入返回正确结果"
  GREEN:    实现基本逻辑
  REFACTOR: 提取辅助函数

循环 3: 边界情况
  RED:      测试 "无效输入抛出错误"
  GREEN:    添加输入验证
  REFACTOR: 统一错误处理
```

## 覆盖率目标

- 行覆盖率 ≥ 80%
- 分支覆盖率 ≥ 70%
- 核心业务逻辑覆盖率 ≥ 90%

## 输出要求

- 说明当前处于 RED、GREEN 还是 REFACTOR
- 标记新增或修改的测试
- 说明尚未覆盖的边界
- 提交时所有测试必须通过
