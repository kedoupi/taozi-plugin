# Plan

根据用户需求 `$ARGUMENTS`，创建结构化的实现计划。

## 何时使用

- 需求跨多个模块或层次，不能一步改完
- 涉及技术选型、架构变动、高风险修改
- 用户明确要求方案、计划、拆分任务

## 核心原则

- 步骤要可直接执行，不写空泛动作
- 优先从低风险、能建立反馈的步骤开始
- 明确哪些可以并行，哪些必须串行
- 给出最小可行版本，不一次做满
- 每个设计抉择必须说明为什么；不回避风险；如需求不明确主动提问

## 执行步骤

### 1. 需求分析

- 提取 `$ARGUMENTS` 中的核心需求
- 识别功能边界：包含什么、不包含什么
- 列出隐含需求（错误处理、边界情况、性能要求）
- 确认技术约束（语言、框架、现有依赖）

```markdown
## 需求摘要
- 核心功能: [一句话描述]
- 用户故事: 作为 [角色]，我希望 [功能]，以便 [价值]
- 边界: 包含 [...] / 不包含 [...]
```

### 2. 代码库探索

- 用 `Glob` + `Grep` 搜索相关文件和模块
- 识别可复用的组件和模式
- 确认需要修改的文件列表

```markdown
## 受影响文件
- `path/to/file.ts` — [修改原因]
- `path/to/new-file.ts` — [新建原因]
```

### 3. 架构设计

- 选择方案，说明 trade-offs
- 定义接口/数据结构
- 确认与现有代码的集成方式

```markdown
## 设计抉择

| 方案 | 优点 | 缺点 | 选择 |
|------|------|------|------|
| 方案 A | ... | ... | ✅ |
| 方案 B | ... | ... | |

## 数据流
[输入] → [处理] → [输出]
```

### 4. 任务拆分

```markdown
## 任务列表

### T1: [任务名称]
- 描述: [具体做什么]
- 文件: [涉及文件]
- 复杂度: 低/中/高
- 依赖: 无 / 依赖 T{n}
```

拆分原则：每个任务可独立测试；单任务不超过 3 个文件；核心路径优先。

### 5. 风险评估

```markdown
## 风险清单

| 风险 | 可能性 | 影响 | 缓解措施 |
|------|--------|------|----------|
| ...  | 高/中/低 | 高/中/低 | ... |
```

### 6. 输出计划

完整计划写入 `plan.md`：

```markdown
# 实现计划: [功能名称]

## 需求摘要
## 受影响文件
## 设计抉择
## 任务列表
## 风险评估
## 验收标准
- [ ] [标准 1]
```
