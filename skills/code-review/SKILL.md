# Code Review

对指定文件、PR 或 `git diff main` 的变更进行全面审查。目标: `$ARGUMENTS`。

## 何时使用

- 用户要求 review、审查、找风险
- 准备合并、发布或质量回归
- 需要明确列出 bug、回归点、安全问题、测试缺口

## 核心原则

- 优先找行为风险，不先做风格评论
- findings 按严重程度排序，具体到文件:行号
- 区分"必须修复"（CRITICAL）和"建议改进"（WARNING/INFO）
- 认可写得好的代码，不只指出问题
- 不做主观风格批评，不要求重构无关代码
- 没有明显问题要明确说"未发现实质性问题"

## 审查清单

- 逻辑是否正确，是否改变原有语义
- 错误处理、边界条件、空值路径是否完整
- 安全基线是否被削弱
- 并发、状态同步、缓存、事务是否可能失效
- 测试是否覆盖主要正反路径

## 执行步骤

### 1. 获取变更内容

```bash
# 默认：相对 main 的变更
git diff main...HEAD --stat && git diff main...HEAD

# 指定文件
git diff main...HEAD -- <file>

# PR 号
gh pr diff <PR号>
```

### 2. 质量检查

- [ ] 命名清晰准确（函数动词开头、类名词）
- [ ] 函数长度不超过 40 行
- [ ] 嵌套层级不超过 3 层
- [ ] 无重复代码（DRY）
- [ ] 注释解释"为什么"而非"做什么"
- [ ] 错误处理完整（不吞异常）
- [ ] 无调试代码残留（console.log、print、TODO）

### 3. 安全审查

- [ ] 无硬编码密钥/密码/Token
- [ ] 用户输入已验证和清理
- [ ] SQL 查询使用参数化
- [ ] 无 eval/exec/动态代码执行
- [ ] 文件操作路径安全（无穿越风险）
- [ ] 敏感数据使用安全存储（Keychain/环境变量）
- [ ] HTTP 请求使用 HTTPS

### 4. 性能分析

- [ ] 无 N+1 查询
- [ ] 无不必要的全量加载
- [ ] 大列表虚拟滚动或分页
- [ ] 无内存泄漏风险（监听器清理）
- [ ] 异步不阻塞主线程
- [ ] 缓存策略合理

### 5. 测试检查

- [ ] 新功能有对应测试
- [ ] 边界情况已覆盖
- [ ] 错误路径已测试
- [ ] 测试描述清晰
- [ ] 无硬编码等待（sleep）

### 6. 最佳实践

- [ ] 符合项目编码规范
- [ ] 正确使用框架特性（React hooks、SwiftUI 等）
- [ ] 依赖注入而非硬依赖
- [ ] 接口设计遵循最小知识原则
- [ ] 类型安全（无 any、无强制解包）

## 报告格式

```markdown
## 代码审查报告

### 概览
- 审查范围: [文件/PR]
- 变更文件数: X / +X -Y 行

### 严重程度统计

| 级别 | 数量 | 说明 |
|------|------|------|
| CRITICAL | X | 必须修复，阻塞合并 |
| WARNING | X | 建议修复 |
| INFO | X | 改进建议 |

### 问题列表

#### CRITICAL
1. `[文件:行号]` — [问题描述]
   - 原因: [为什么是问题]
   - 建议: ```[修复代码片段]```

#### WARNING / INFO
1. `[文件:行号]` — [问题 / 建议]

### 总体评价
- 代码质量 / 安全性 / 可维护性
- 建议: [合并 / 修改后合并 / 需重做]
```
