# 深度研究工作流

用于技术调研、方案评估、复杂问题的系统性分析。

## 何时使用

- 技术选型（框架/库/架构/数据库）
- 不熟悉的领域快速建立认知
- 方案对比与决策支持
- 复杂 Bug 的根因分析
- 性能问题的系统性排查

## 研究框架

### 第一步：明确研究问题

```markdown
## 研究问题定义

**核心问题**: [一句话]

**背景约束**:
- 技术栈: [当前使用的语言/框架]
- 规模: [团队大小/项目规模/流量]
- 时间: [上线时间/迁移窗口]
- 成本: [预算约束]

**成功标准**: [如何判断研究完成，决策有依据]
```

### 第二步：信息收集

```markdown
## 信息来源优先级

1. 官方文档 / Changelog（最权威）
2. GitHub Issues / PR（真实问题反馈）
3. 技术博客（实践经验）
4. Stack Overflow（具体问题解法）
5. 基准测试数据（性能对比）
```

### 第三步：方案对比矩阵

```markdown
## 方案对比

| 维度 | 方案 A | 方案 B | 方案 C |
|------|--------|--------|--------|
| 成熟度 | ★★★★★ | ★★★★☆ | ★★★☆☆ |
| 性能 | 高 | 中 | 高 |
| 学习曲线 | 低 | 中 | 高 |
| 社区活跃度 | 高 | 中 | 低 |
| 维护成本 | 低 | 中 | 高 |
| 适合团队规模 | 小/中 | 中/大 | 大 |

**我们的权重**: 成熟度 30% + 性能 25% + 学习曲线 20% + 社区 25%

**加权得分**: A: X分 / B: Y分 / C: Z分
```

### 第四步：风险分析

```markdown
## 风险矩阵

| 风险 | 概率 | 影响 | 缓解措施 |
|------|------|------|---------|
| 供应商停止维护 | 低 | 高 | 选择开源，fork 能力 |
| 性能不达预期 | 中 | 中 | PoC 验证 |
| 团队学习成本 | 高 | 低 | 培训计划 |
```

### 第五步：决策建议

```markdown
## 决策建议

**推荐方案**: [选项]

**理由**:
1. [最重要的原因]
2. [第二原因]
3. [第三原因]

**前提条件**:
- [条件1才成立]
- [如果X，则改选Y]

**下一步行动**:
1. [ ] PoC 验证：[具体验证点]
2. [ ] 团队培训：[资料/时间]
3. [ ] 迁移计划：[阶段/里程碑]
```

## 常用研究模式

### 技术选型研究

```markdown
调研框架：
1. 核心功能是否满足（必要条件）
2. 性能基准（实测或官方数据）
3. 生态成熟度（npm 下载量/GitHub stars/最近 commit）
4. 已知问题（GitHub Issues 前 20）
5. 迁移复杂度（如果将来要换）
```

### Bug 根因研究

```markdown
根因分析步骤：
1. 复现问题（最小可复现案例）
2. 排除法缩小范围
3. 查看相关 changelogs（版本升级引入？）
4. 搜索同类 Issues（GitHub/Stack Overflow）
5. 阅读源码确认根因
6. 验证修复（而非 workaround）
```

### 性能问题研究

```markdown
性能研究框架：
1. 建立基准（before 数据）
2. 分析 profiling（找热点）
3. 假设原因（1-3个）
4. 逐一验证（控制变量）
5. 测量改进（after 数据）
6. 记录结论（防止重蹈）
```
